CHAPTER 13Part IV · Systems & Control

Meta-Prompting & Self-Optimizing Prompts

What happens when prompts stop being hand-crafted strings and become source code compiled from a specification? DSPy, APE, OPRO, TextGrad — the 2023–2026 shift from prompt engineering to prompt programming.

2022-11 APE (Zhou et al.) 2023-10 DSPy v0.1 (Stanford) 2023-12 OPRO (Google) 2024-06 TextGrad (Stanford) 2024-08 MIPRO teleprompter 2024-11 PromptWizard (Microsoft) 2025-2026 DSPy in production
🧒 ELI5 — explain like I'm five

Imagine writing a prompt as a long paragraph: "You are a helpful assistant. Please answer the question carefully…" That's like writing machine code: fragile, task-specific, and nobody remembers why it says what it says six months later.

DSPy is like Python for prompts. You declare what you want — "given a question, produce a short answer with citations" — and a compiler figures out how to prompt the model to do it, by trying many variations and measuring which works best on a small set of labelled examples. When you upgrade to a new model, you re-compile. The code stays the same; the prompts get regenerated.

TextGrad goes further: the prompt is improved by natural-language gradients — "your output was wrong because you ignored constraint X" becomes an edit to the prompt itself.

13.1 The Prompt-Engineering Bottleneck

Volume II Chapter 3 treated prompting as a craft. For one task, crafted prompts work. At scale — an org with hundreds of LLM-powered features, each with its own prompt, each needing to survive model upgrades — the craft becomes unmaintainable.

Three symptoms:

  • Upgrade tax. A prompt tuned for GPT-4 regresses on Claude. A Claude-tuned prompt regresses on Opus 4.7. Re-tune by hand every few months.
  • Silent skill rot. Nobody owns the prompt. Quality drifts as edge cases accrete.
  • No evals. You have the prompt; you don't have the test set that proves it works.

Meta-prompting argues: the prompt should be compiled from a specification plus an eval set, not written by hand.

13.2 DSPy — Prompts as Source Code

Khattab et al.'s DSPy (Stanford 2023-ongoing) models an LLM program as a pipeline of modules with typed signatures. A teleprompter (the "compiler") takes your program + a metric + a small labelled dev set and produces a compiled program — the same modules, with their prompts (instructions, few-shot examples, output format) filled in by search.

DSPy: you write the program once, declare a metric and a dev set, and a teleprompter compiles it into working prompts. Model upgrade = recompile.

Core DSPy abstractions:

  • Signature — a typed input/output contract: "question → answer" or "context, question → rationale, answer".
  • Module — a callable with a signature. Predict, ChainOfThought, ReAct, ProgramOfThought.
  • Teleprompter — an optimiser. BootstrapFewShot bootstraps examples from the dev set; MIPRO jointly optimises instructions + few-shot; COPRO uses the LLM to propose instruction variants.
import dspy

# 1. declare a program
class RAG(dspy.Module):
    def __init__(self):
        self.retrieve = dspy.Retrieve(k=3)
        self.gen = dspy.ChainOfThought("context, question -> answer")
    def forward(self, question):
        ctx = self.retrieve(question).passages
        return self.gen(context=ctx, question=question)

# 2. compile
teleprompter = dspy.teleprompt.MIPRO(metric=exact_match_f1)
rag_compiled = teleprompter.compile(RAG(), trainset=dev_set)

# 3. use — the compiled program behaves like the original
rag_compiled("Who wrote Hamlet?")

13.3 APE & OPRO — the LLM as its Own Optimiser

APE (Automatic Prompt Engineer, Zhou et al. 2022): ask an LLM to generate candidate prompts, score each on dev data, take the best. The original "LLM optimises its own prompt" paper.

OPRO (Optimization by PROmpting, Yang et al. Google 2023): make the LLM an iterative optimiser. Feed it the trajectory of "prompts tried so far + scores" and ask for the next one. Works on arbitrary black-box objectives — traveling salesman, linear regression, prompts.

OPRO's funnier finding: the best prompt it discovers for math is "Take a deep breath and work on this problem step-by-step." Empirical fact, not a joke.

13.4 TextGrad — Natural-Language Gradients

Yuksekgonul et al. (Stanford 2024) treat an LLM pipeline like a differentiable program where the "gradients" are free-form text. A wrong output is fed back to a "judge" LLM: "the output was wrong in this way; what should we change?" The judge's response is an edit to the upstream prompt. Iterate.

This is not gradient descent in the mathematical sense — but it's the right interface: you can compose TextGrad'd pipelines and "differentiate through" them.

13.5 Meta-Prompts Inside Agents

Inside a running agent, meta-prompting appears as:

  • Self-rewriting system prompts. At the end of a task, the agent reflects on what went wrong and proposes an edit to its own system prompt. Used by Anthropic's Claude Code skill-creator pattern.
  • Dynamic prompt composition. Select which sub-prompts to load based on the current state. Skills (Vol II Ch 06) are a special case.
  • Prompt chaining with judges. Each step's output is judged; a failing judgment triggers a rewrite or retry with modified instructions.

13.6 Reference — Mini-DSPy

"""~120-line mini-DSPy for teaching. Production: use dspy-ai."""
import dataclasses, random
from typing import Callable

@dataclasses.dataclass
class Signature:
    inputs: list[str]
    outputs: list[str]

class Predict:
    def __init__(self, sig: Signature, llm: Callable):
        self.sig, self.llm = sig, llm
        self.demos: list[dict] = []             # few-shot traces
        self.instruction: str = "Follow the signature."

    def _prompt(self, **kw):
        parts = [self.instruction]
        for d in self.demos:
            parts.append("Example:")
            for f in self.sig.inputs:  parts.append(f"{f}: {d[f]}")
            for f in self.sig.outputs: parts.append(f"{f}: {d[f]}")
        parts.append("Now answer:")
        for f in self.sig.inputs:  parts.append(f"{f}: {kw[f]}")
        for f in self.sig.outputs: parts.append(f"{f}:")
        return "\n".join(parts)

    def __call__(self, **kw):
        text = self.llm(self._prompt(**kw))
        return parse_fields(text, self.sig.outputs)

class BootstrapFewShot:
    """Simplest teleprompter: bootstrap demos from dev set."""
    def compile(self, module: Predict, trainset, metric, k=6, trials=8):
        best, best_score = None, -1
        for _ in range(trials):
            candidate = random.sample(trainset, k)
            module.demos = candidate
            score = sum(metric(module(**x), x) for x in trainset) / len(trainset)
            if score > best_score:
                best, best_score = list(candidate), score
        module.demos = best
        return module
Prompts as source code

Hand-crafted prompts are a liability. DSPy-style compilation survives model upgrades, generalises across tasks, and comes with evals built in. The "prompt engineer" job title is a transitional artefact.

— Khattab (DSPy), Stanford NLP, production RAG teams

Meta-prompting as a crutch

If you have an eval set, fine-tune. If you don't, meta-prompting is over-fitting to the dev set. DSPy-compiled prompts are opaque, brittle across distribution shift, and harder to debug than the prompts they replace. Prompt engineers aren't going anywhere.

— parts of the Anthropic engineering team, most working prompt engineers

❓ Open questions

  • Is meta-prompting really better than a very short fine-tune at the same data cost?
