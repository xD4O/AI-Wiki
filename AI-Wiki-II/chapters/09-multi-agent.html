CHAPTER 09 Part III · Agents

Multi-Agent Systems

When (and when not) to let a team of specialized agents beat one big model. Orchestrator-worker, debate, failure modes, and the frameworks that matter in 2026.

9.1 Why Multi-Agent

A single long agent loop can do almost anything. But four forces push toward multi-agent:

  • Specialization. A "planner" model tuned for planning and an "executor" tuned for execution both do better than one jack-of-all-trades.
  • Parallelism. Independent subtasks can run concurrently.
  • Isolation. Each sub-agent has its own context window — no pollution of the main loop.
  • Oversight. An explicit "critic" agent is easier to reason about than a single self-reflecting loop.
Multi-agent is often worse than single-agent

Anthropic, OpenAI, and Cognition have all published on this: for most tasks, one capable model in a tight ReAct loop beats an ensemble. Communication overhead, cascading errors, and unbounded cost eat the specialization gains. Reach for multi-agent only when you can name the specific force it unlocks.

9.2 Orchestrator + Workers

The most reliable pattern. A single orchestrator holds the overall goal and state. It dispatches subtasks to workers — each a focused sub-agent with its own context, tools, and success criterion. Workers return structured results; the orchestrator aggregates.

Orchestrator-worker: specialists, each with a scoped context, reporting to one head.

9.3 Debate, Critique, Ensemble

  • Debate. Two agents argue opposing positions; a judge decides. Useful for ambiguous calls (content moderation, research synthesis).
  • Critique. One agent produces, another audits. When the auditor is stricter than the producer, quality goes up monotonically.
  • Ensemble. Run N agents independently on the same task; vote. Gains diminish quickly past ~3.

9.4 Swarms — Caveat Emptor

"Let N agents emerge a solution together" makes for good demos and bad production. Without a strict orchestrator, swarms drift, deadlock, or converge on mediocre consensus. If you reach for a swarm, at least pin a coordinator.

9.5 Communication Protocols

  • Shared memory. A key-value store all agents can read/write. Simple; race-prone.
  • Message passing. Typed messages between named agents. Easier to observe and trace.
  • Filesystem rendezvous. Each agent writes to a scratch dir; orchestrator reads. This is what Claude Code's sub-agents do — simple, debuggable, every exchange persists.

9.6 Failure Modes

  • Cascading hallucinations. One agent's fabricated fact becomes another's "retrieved context."
  • Deadlocks. Agent A waits on B; B waits on A.
  • Unbounded cost. Loops with no termination condition burn thousands of dollars.
  • Lost goal. After many hops, nobody remembers the original ask.
  • Prompt-injection amplification. A compromised worker can manipulate the orchestrator.

Mitigations: budget caps (hard max on calls / tokens / wall-clock), typed results, distinct "goal owner" role, orchestrator checks after every N workers.

9.8 Code — a 3-Agent Code Review

# A toy orchestrator that runs planner → coder → critic.
# Uses one shared conversation list and distinct system prompts.

def subagent(system, user, model="claude-opus-4-7"):
    r = client.messages.create(model=model, system=system, max_tokens=2000,
                               messages=[{"role": "user", "content": user}])
    return r.content[0].text

def review(diff):
    plan   = subagent("You are a code-review planner. List 3-5 things to check.", diff)
    review = subagent("You are a senior reviewer. Do the review following this plan:\n" + plan, diff)
    critic = subagent("You are a staff engineer. Reject vacuous or wrong claims in this review.",
                      f"DIFF:\n{diff}\n\nREVIEW:\n{review}")
    return critic

Run the same diff through single-agent ReAct and you'll often find one-shot is faster and comparable. Multi-agent earns its keep on long, heterogeneous tasks — not short ones.
