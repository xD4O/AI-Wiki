CHAPTER 07 Part III · Agents

MCP — the Model Context Protocol

The open standard for plugging tools and data into any model, portably. JSON-RPC over stdio / SSE / HTTP. Three primitives: tools, resources, prompts.

7.1 Why MCP Exists

Before MCP, every model host (Claude Desktop, Cursor, Zed, Open WebUI) invented its own plugin system, and every integration vendor (GitHub, Notion, Postgres) had to ship N different wrappers. M hosts × N integrations = N·M work. MCP collapses that to M + N: each host implements the MCP client once, each integration publishes an MCP server once.

MCP is the "USB-C for AI integrations."

7.2 The Protocol — JSON-RPC & Three Primitives

MCP is JSON-RPC 2.0 over one of three transports:

  • stdio — the client spawns the server as a subprocess. Simplest. Default for local tools.
  • Streamable HTTP — remote servers. Supports streaming and sessions.
  • SSE — legacy, gradually being retired in favour of Streamable HTTP.

A server exposes three primitives:

PrimitivePurposeAnalogous to…
ToolsSide-effecting actions the model can callFunction calls
ResourcesRead-only data the host can surface or the model can requestURIs / files
PromptsReusable parameterized prompt templatesSlash commands

A wire-level example

// client → server (over stdio)
{"jsonrpc": "2.0", "id": 1, "method": "initialize",
 "params": {"protocolVersion": "2025-11-25", "capabilities": {}}}

// server → client
{"jsonrpc": "2.0", "id": 1, "result": {
   "protocolVersion": "2025-11-25",
   "serverInfo": {"name": "fs-server", "version": "1.0"},
   "capabilities": {"tools": {}, "resources": {}}}}

// client asks what tools exist
{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}

// server returns
{"jsonrpc": "2.0", "id": 2, "result": {"tools": [
  {"name": "read_file", "description": "Read a file",
   "inputSchema": {"type": "object", "properties": {"path": {"type": "string"}}}}
]}}

// model emits a tool_use; client forwards
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "read_file", "arguments": {"path": "README.md"}}}

// server returns the content
{"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "# My project..."}]}}

7.3 Servers, Clients, Hosts

  • Host — the user-facing app (Claude Desktop, Claude Code, Cursor). Manages user consent and the LLM call.
  • Client — a thin connector inside the host that speaks MCP. One per server.
  • Server — the thing providing tools/resources/prompts. Usually a small Python or Node process.

7.4 Security Model & the Confused Deputy

The confused deputy

If your MCP server has broad access (e.g., your whole filesystem, your DB) and the host forwards every model-requested tool call without checks, prompt injection in any retrieved document becomes a privilege-escalation vector. The host MUST mediate — that's the 2025-11-25 spec's core safety claim.

Recommendations:

  • Run sensitive servers (DB, shell) with the least-privilege credentials they need.
  • Prompt the user for consent on the first invocation of a dangerous tool.
  • For remote servers: use the OAuth 2.1 + PKCE flow defined in the spec.
  • Keep allow-lists of domains the model can actually hit with fetch-style tools.

7.5 Popular Servers

  • filesystem — scoped read/write/glob.
  • github — issues, PRs, code search.
  • postgres — schema introspection + parameterized SQL.
  • slack, linear, notion, google-drive.
  • playwright — browser automation, screenshots, DOM inspection.
  • sqlite, memory (key-value), sequentialthinking (scratchpad).

The community has curated lists at punkpeye/awesome-mcp-servers and wong2/awesome-mcp-servers.

7.6 Build Your Own Server (Python)

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def get_forecast(city: str) -> str:
    """Return a short weather forecast for the given city."""
    return f"Forecast for {city}: sunny, 22°C."

@mcp.resource("weather://{city}/history")
def history(city: str) -> str:
    """Last 7 days of weather."""
    return f"History for {city}: ..."

if __name__ == "__main__":
    mcp.run()  # speaks stdio by default

Register it with Claude Code by dropping this into ~/.claude.json:

{
  "mcpServers": {
    "weather": {"command": "python", "args": ["./weather_server.py"]}
  }
}

7.7 Build Your Own Client

from mcp import ClientSession, stdio_client
import asyncio

async def main():
    async with stdio_client(command="python", args=["./weather_server.py"]) as (r, w):
        async with ClientSession(r, w) as session:
            await session.initialize()
            tools = await session.list_tools()
            print([t.name for t in tools.tools])
            result = await session.call_tool("get_forecast", {"city": "Paris"})
            print(result.content[0].text)

asyncio.run(main())

7.8 Debugging with MCP Inspector

# Inspector spawns your server and gives you a UI to exercise each primitive
npx @modelcontextprotocol/inspector python ./weather_server.py

The inspector shows capability negotiation, lists tools/resources, lets you call them with arbitrary JSON, and surfaces schema validation errors — use it before you ever hook a server into a real model.

7.9 Where MCP Is Going (2026)

Governance moved to the Agentic AI Foundation in 2025 and is now managed via open Working Groups. The 2026 roadmap emphasizes:

  • Transport scalability. Streamable HTTP is the new default; long-running SSE is being retired.
  • Enterprise auth. SSO, audit logs, signed manifests, gateway patterns.
  • Agent-to-agent communication. A formalized way for one MCP-aware agent to expose capabilities to another.
  • Registry. A canonical way to discover, version, and trust servers.
